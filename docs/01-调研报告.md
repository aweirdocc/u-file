# u-file · 调研报告

> 调研日期：2026-09-30
> 事实与引用的完整版见 [research/01-技术调研笔记.md](./research/01-技术调研笔记.md)，本文只保留结论与决策。

## 1. 调研目的

回答三个问题：

1. "聚合多种文件源 + Web 浏览"这个赛道是否已有成熟开源方案？能否直接用？
2. 各家对象存储（国内大厂 + Cloudflare R2）的 S3 兼容性是否足以支撑"一套驱动统一接入"？
3. FTP / SFTP / 数据库存文件（BLOB / GridFS）在 Go 生态里是否有可靠的实现基础？

## 2. 同类开源产品对比

| 项目 | 定位 | 支持的文件源（与本需求相关部分） | 数据库文件源 | 许可证 | 维护状态（2026-09） |
|---|---|---|---|---|---|
| AList | 多存储聚合挂载 + Web 浏览，赛道标杆 | 本地、S3、FTP、SFTP、WebDAV、SMB、Azure Blob + 大量网盘 | ❌ 无 | AGPL-3.0 | 活跃（star ≈ 50k）；2025-06 因移交商业公司引发社区信任危机 |
| OpenList | AList 社区分叉（Anti Trust Crisis），延续其路线 | 同上（`drivers/` 目录实查） | ❌ 无（无 GridFS、无任何 BLOB 类驱动） | AGPL-3.0 | 活跃（star ≈ 25k） |
| Cloudreve | 自建网盘（V4），偏"个人/团队云盘" | 本地、从机、OSS、COS、OBS、Kodo、KS3、又拍云、OneDrive、S3 兼容 | ❌ 无 | GPL-3.0 | 活跃（star ≈ 29k） |
| FileBrowser | 本地目录的 Web 文件管理 | 仅本地目录 | ❌ | Apache-2.0 | **仓库已归档（只读）** |
| Seafile / Nextcloud | 企业同步盘 / 私有云协作平台 | 重产品，非"多源聚合网关"定位 | ❌ | 自有双许可 / AGPL 系 | 活跃，但体量与定位不符 |
| MinIO | S3 兼容对象存储**服务端**（不是聚合浏览工具） | — | — | AGPL-3.0 | **官方仓库 2026-04-25 归档** |
| SFTPGo | 多协议文件**服务器**（反向参考） | 把本地/S3/GCS/Azure/远端 SFTP/FTP 通过 SFTP/FTP/WebDAV/HTTP 暴露 | ❌ | AGPL-3.0 | 活跃 |

关键结论：**"聚合浏览"有成熟方案（AList/OpenList），但没有任何一个项目支持数据库类文件源**（MySQL/PG BLOB、PG Large Object、MongoDB GridFS）；且头部项目均为 AGPL/GPL，若不打算以同样许可证开源，不能直接拷码。

## 3. 关键发现

### 3.1 S3 兼容是"事实标准"，但各有暗礁

七家对象存储（阿里云 OSS、腾讯云 COS、华为云 OBS、七牛 Kodo、百度 BOS、Cloudflare R2、MinIO）官方都提供 S3 兼容入口，**用 aws-sdk-go-v2 + 可配置 endpoint/path-style 统一接入的路线成立**。但每家都有需要单独处理的差异：

- **OSS**：不支持 `aws-chunked` 传输编码；不支持跨 region 重定向；建议 virtual-hosted style
- **COS**：官方明示"不保证与 S3 完全兼容"；**2024-01-01 之后创建的桶不再支持 path-style 域名**
- **OBS**：兼容 S3（V2/V4 签名），但其官方"S3 兼容说明"文档页当前 404，只能以实测为准
- **Kodo**：path-style 与 virtual-hosted 均可；必须携带 AWS 签名（不支持匿名）
- **BOS**：有专门的官方"S3 兼容"文档章节
- **R2**：对象级核心 API（ListObjectsV2、分片上传、Range、预签名 URL ≤ 7 天）完整支持；**不支持版本控制、ACL、对象 tagging、Object Lock、SSE-S3/SSE-KMS**；`x-amz-storage-class` 仅 STANDARD/STANDARD_IA
- **MinIO**：标准 S3 + path-style 即可；注意其服务端仓库已归档（不影响协议接入）

结论：**path-style/virtual-hosted、签名版本、直链有效期等必须做成"每源可配"**，并为每家建立实测冒烟清单，而不是依赖文档承诺。

### 3.2 FTP / SFTP 的 Go 基础扎实，可直接锁定选型

- **FTP**：`jlaffaye/ftp`（v0.2.4，2026-08，ISC）支持 MLSD 目录列表、显式 TLS（FTPS）、流式下载（`Retr`）与断点（`RetrFrom`），并有防 SSRF 的 PASV IP 策略选项。注意：不支持隐式 TLS（990 端口）。
- **SFTP**：`pkg/sftp`（v1.13.11）+ `golang.org/x/crypto/ssh`，密码/私钥认证齐备，并发读默认开启；约束：单包上限 32KiB、并发写失败需 Truncate 补偿、host key 校验必须产品化（不能默认跳过）。

### 3.3 数据库文件源：必须自研，且要"分级承诺"

- **MongoDB GridFS**：官方驱动提供真流式读写（`OpenUploadStream`/`OpenDownloadStream`），体验最佳
- **PostgreSQL Large Object**：`pgx` 支持流式读写，但**必须在事务内使用**（会话层需长事务管理）
- **MySQL BLOB / PG bytea**：驱动无流式读取（go-sql-driver 有开放 feature request），单值整体载入内存；缓解手段是 `SUBSTRING` 分块读（社区实践、非官方推荐）——**产品上必须限制文件大小与性能预期**

这正好是所有同类产品的空白，构成 u-file 的差异化能力。

### 3.4 生态风险信号

- MinIO（2026-04）与 FileBrowser 仓库相继归档：**自建轻量聚合层的合理性增加**——即使不做 u-file，"把 S3 兼容端点当唯一依赖"也比"绑定某个具体开源存储产品"更稳。
- AList 的商业化风波说明：以 AGPL 单点项目作为长期基础设施有信任风险；u-file 自研驱动层 + 参考公开协议文档是安全路径。

## 4. 差异化定位（立项依据）

| 对比维度 | AList / OpenList | Cloudreve | u-file（本方案） |
|---|---|---|---|
| 核心定位 | 个人多源聚合/网盘挂载 | 自建网盘 | **工程化的统一文件门户** |
| 数据库文件源 | ❌ | ❌ | ✅ GridFS / PG Large Object / BLOB 表（分级） |
| 凭据安全与审计 | 弱（明文可导出场景多） | 一般 | 加密落库、不回显、审计日志（企业向基线） |
| 许可证 | AGPL-3.0 | GPL-3.0 | 自主选择（自研代码） |
| 部署形态 | 单二进制 | 单二进制 | 单二进制 + Docker（对齐习惯） |

**结论：立项成立。** 技术上没有不可行的环节；核心工作量在于各协议差异的适配与长期兼容性维护，用"能力位 + 每源配置 + 实测冒烟矩阵"来收敛。
