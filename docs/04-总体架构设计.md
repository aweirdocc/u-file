## 1. 总体架构

```
┌─────────────────────────────────────────────────────────┐
│                    Web 前端 (Vue 3 + TS)                 │
│        源管理 · 文件浏览 · 预览 · 设置 · 任务状态          │
└──────────────────────────┬──────────────────────────────┘
                           │ REST (JSON) / 下载走流式响应
┌──────────────────────────▼──────────────────────────────┐
│                     API 层 (Gin/chi)                     │
│     鉴权 · 参数校验 · 能力位过滤 · 错误码 · 审计埋点       │
├─────────────────────────────────────────────────────────┤
│                      核心服务层                           │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌────────────┐  │
│  │ 源管理    │ │ 文件浏览  │ │ 传输网关  │ │ 索引/同步   │  │
│  │ CRUD+测试 │ │ 列表+搜索 │ │ 下载/上传 │ │ 定时+缓存   │  │
│  └────┬─────┘ └────┬─────┘ └────┬─────┘ └─────┬──────┘  │
│       └────────────┴─────┬──────┴─────────────┘         │
│                 统一文件系统抽象 (FSDriver 接口)           │
├─────────────────────────────────────────────────────────┤
│                     驱动层（插件式）                       │
│ local │ s3 │ webdav │ gdrive │ alipan │ ftp/sftp │ db   │
├─────────────────────────────────────────────────────────┤
│  元数据库 (SQLite/MySQL/PG)：用户·源配置·索引·分享·审计    │
└──────────────────────────┬──────────────────────────────┘
                           ▼
   外部存储：OSS/COS/OBS/Kodo/BOS/R2/MinIO/S3 · FTP 服务器
             · SFTP 服务器 · MySQL/PG/Mongo(文件表/GridFS) · 本地盘
```

分层职责一句话版：

- **前端**：纯静态资源，由后端同端口托管，也支持独立部署
- **API 层**：HTTP 协议适配，不含业务逻辑；按驱动能力位决定暴露哪些操作
- **核心服务层**：源管理、浏览编排（缓存优先、回源兜底）、流式传输网关、索引同步任务
- **驱动层**：唯一与外部协议打交道的地方，每个驱动只实现接口 + 声明能力位
- **元数据库**：平台自身数据（不含文件内容）

## 2. 技术栈选型

| 层 | 选型 | 理由（详见可行性分析） |
|---|---|---|
| 后端语言 | **Go 1.22+** | 单二进制交付、并发模型适合流式传输、各协议 SDK 成熟 |
| HTTP 框架 | Gin（或 chi） | 生态成熟、中间件丰富、`http.ServeContent` 天然支持 Range |
| ORM/DB 访问 | GORM（或 sqlx） | 元数据库 CRUD 简单为主 |
| 元数据库 | SQLite（默认）/ MySQL / PostgreSQL | 零依赖开箱即用，可平滑升级 |
| 前端 | Vue 3 + TypeScript + Element Plus + Pinia + Vite | 组件丰富（表格/树/上传/对话框齐备），国内生态好 |
| 部署 | 单二进制 / Docker | 对标同类开源产品的部署习惯 |

## 3. 核心设计：统一文件系统抽象（驱动接口）

这是整个平台的基石。所有"源"的差异被隔离在驱动里，上层只面向接口。

> **M0 落地调整（2026-10-27）**：为避免早期接口反复变动，M0 只固化读路径（List/Stat/Open 必需接口 + Presigner 可选接口，见 `internal/driver/driver.go`），写能力（Upload/Remove/Rename/Mkdir）在 M1 以独立可选接口加入；能力位结构保持不变。另外，**源管理已提前落地**（原属 M1）：`internal/source.Manager` 提供增删/测试/持久化（`data/sources.json`，原子写），Web 弹窗 + REST 可即时增删源、测试连接，凭据打码回显；加密落库仍在 M1。以下为完整设计，标注 *(M1+)* 的部分尚未实现。

```go
// 驱动能力位：驱动声明自己支持什么，上层据此决定 UI 与 API 行为
type Capabilities struct {
    List, Stat, Download      bool // 基础能力：全部驱动必须支持
    Upload, Delete            bool
    Rename, Mkdir, Move, Copy bool
    PresignURL                bool // 可生成带签名的直链（S3 族；M0：按是否配置凭据声明）
    ListCursor                bool // 列目录支持分页游标（S3: continuation token）
    MaxListPageSize           int
}

type Entry struct {
    Path    string    // 相对源根路径，统一以 / 分隔
    Name    string
    IsDir   bool
    Size    int64
    ModTime time.Time
    ETag    string    // 有则用于增量同步与秒传判断
    MimeType string
}

type FSDriver interface {
    // 名称/类型标识，如 "s3"、"ftp"、"sftp"、"mysql-blob"
    Scheme() string
    Capabilities() Capabilities

    // —— 基础能力 ——
    List(ctx context.Context, dir string, opt ListOptions) (*ListResult, error) // 支持游标分页
    Stat(ctx context.Context, path string) (*Entry, error)
    // Open 必须返回流：不整载内存；支持 Range（不支持的驱动由网关降级为全量+跳读）
    Open(ctx context.Context, path string, opt RangeOptions) (io.ReadCloser, error)

    // —— 可选能力（不支持返回 ErrNotSupported）——
    Mkdir(ctx context.Context, dir string) error
    Remove(ctx context.Context, path string, recursive bool) error
    Rename(ctx context.Context, from, to string) error
    Upload(ctx context.Context, path string, r io.Reader, size int64) error
    // 直链（S3 族）：返回带签名的 GET URL
    PresignGet(ctx context.Context, path string, ttl time.Duration) (string, error)
}

// DriverFactory：按源配置实例化驱动
type DriverFactory func(cfg SourceConfig) (FSDriver, error)
```

设计要点：

1. **面向流**：`Open` 返回 `io.ReadCloser`，下载网关直接 `io.Copy` / `http.ServeContent`，天然支持 Range 与大文件，内存占用 = 缓冲区大小。M0 实测：1GB 文件、3 路并发，服务端峰值内存 ~16MB（见 [m0-poc-验证记录](./m0-poc-验证记录.md)）。
2. **能力位驱动 UI**：前端根据源的能力位渲染按钮（如 FTP 源不显示"生成直链"），后端同理拦截不支持的 API 调用。M0 已实现：local 源不显示直链按钮，API 返回 NOT_SUPPORTED。
3. **游标分页**：S3 有 continuation-token、数据库有 offset，FTP 无游标则一次全量返回（`ListCursor=false` 时上层按全量处理）。
4. **驱动无状态**：连接池 / 会话由驱动内部管理（如 SFTP 保持长连接 + 请求并发上限），配置变更时重建实例。
5. **可选接口探测**（M0 模式）：`Presigner`（直链）等可变能力用 Go 接口断言探测（`if p, ok := drv.(driver.Presigner); ok`），新增能力不再膨胀 Capabilities 结构。

## 4. 元数据索引与缓存

### 4.1 策略：懒加载缓存 + 定时同步（双轨）

- **懒加载（读路径）**：用户浏览目录时，先查本地 `nodes` 缓存（TTL 可配，默认 60s）；过期或未命中则实时调驱动列取，写回缓存。保证"新接入的源立即可浏览"。
- **定时同步（后台）**：按源配置周期（如每 6 小时）全量/增量扫描，重建 `nodes`。增量依据：S3 的 ETag / continuation、数据库的 `updated_at` 游标。定时同步主要服务于**跨源搜索**（P1）。
- **写后失效**：通过平台执行的写操作（上传/删除/重命名）成功后，立即失效对应目录缓存，避免"删了还在"的错觉。外部直改存储导致的不一致由 TTL/定时同步收敛——这是聚合类产品的天然边界，需在 UI 上提供"强制刷新"。

### 4.2 核心表结构（元数据库）

```
users        (id, username, password_hash, role, created_at)
sources      (id, name, type, root_path, config_enc BLOB,   -- config 含 endpoint/凭据，AES-GCM 加密
              enabled, list_ttl, sync_cron, remark, created_at)
nodes        (id, source_id, path, name, parent_path, is_dir,
              size, mod_time, etag, mime_type, synced_at,
              UNIQUE(source_id, path), INDEX(parent_path))
sync_jobs    (id, source_id, status, started_at, finished_at, error, scanned)
shares       (id, token, source_id, path, expires_at, password_hash,
              max_downloads, download_count, created_by)
audit_logs   (id, user_id, action, source_id, path, ip, created_at, detail)
```

索引设计要点：`nodes` 用 `(source_id, parent_path)` 支撑目录浏览，`name LIKE 'x%'` 前缀搜索靠普通索引即可，模糊搜索 P1 再考虑 FTS。

## 5. 传输网关

### 5.1 下载

- 统一入口 `GET /api/v1/sources/{id}/download?path=...`（登录态/分享 token 鉴权）
- 实现：驱动 `Open(Range)` → `http.ServeContent`，自动处理 Range/If-Range/断点续传；`Content-Type` 取 Entry.MimeType 或探测
- **直链模式**（仅 `PresignURL=true` 的源）：网关返回 302 → 预签名 URL。省服务器带宽，但注意：① URL 有效期与权限脱钩的风险（签出后无法撤回）；② 内网部署时浏览器需能直连存储 endpoint。默认关闭，按源开启。

### 5.2 上传（P1）

- 小文件（默认 < 100MB）：浏览器 multipart → 网关流式落盘/推给驱动，不落本地临时文件
- 大文件：S3 族走 multipart upload；FTP 走 `REST` 断点；SFTP 按 offset seek 写
- 数据库源（P2）：MVP 只读；写入限制单文件 ≤ 16MB（整块 INSERT），后续再评估分块拼接

### 5.3 并发与限流

- 每源一个信号量（默认并发 8，可配），防止把老 FTP/SFTP 服务器打挂
- 全局传输带宽/连接数上限（可配）

## 7. 安全设计

| 风险 | 对策 |
|---|---|
| 凭据泄露 | 源配置（含 AK/SK、FTP 密码、数据库连接串）AES-256-GCM 加密落库；主密钥来自环境变量/配置文件；API 永不回显明文 |
| 路径穿越 | 所有 path 统一规范化（拒绝 `..`、绝对路径注入、空字节）；驱动层再校验一次 |
| SSRF | 用户可配置的 endpoint 属于预期功能，但提供"允许的网段/端口策略"开关（默认允许任意，内网场景可收紧）；HTTP 客户端禁用自动重定向跟随 |
| 越权 | JWT 会话 + 源级 ACL（P2 起：用户↔源↔读写权限）；分享 token 单独作用域，仅限指定 path |
| 弱口令/爆破 | 登录失败限速；密码强度校验；支持外接反代做进一步限制 |
| 密码传输 | 登录/引导/改密请求中的密码由前端用服务端公钥（`GET /auth/pubkey`）做 RSA-OAEP(SHA-256) 信封加密后提交（载荷含时间戳，±5 分钟防重放）；服务端私钥存 `data/login.key`（0600）。**应用层加密不能防御主动 MITM**，生产仍需 HTTPS/TLS；浏览器非安全上下文（HTTP 且非 localhost）无 `crypto.subtle` 时自动回退明文，此时必须依赖 TLS |
| 审计 | 登录、源变更、下载（可选）、删除/重命名/上传均写 `audit_logs` |

## 8. 部署与交付

- **单二进制**：`u-file serve --config config.yaml`，默认 SQLite + 内嵌前端静态资源
- **Docker**：官方镜像 + docker-compose 示例（u-file + MySQL/PG/Mongo/MinIO/vsftpd 可选，用于联调）
- 配置示例（节选）：

```yaml
server:
  port: 8080
  data_dir: ./data          # SQLite、缓存、日志

  master_key_env: UFILE_MASTER_KEY   # 32 字节，凭据加密主密钥
  allowed_private_network: true       # 内网 endpoint 策略

  - name: 生产备份FTP
    type: ftp
    config:
      host: 10.0.0.8
      port: 21
      username: backup
      # password 通过 Web 界面录入后加密落库
```
