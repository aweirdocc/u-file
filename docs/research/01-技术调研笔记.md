## B. S3 兼容性核实

### 5. 阿里云 OSS

**结论**：OSS 官方声明"兼容 AWS S3 API"，S3 兼容 endpoint 为 `https://s3.oss-{region}.aliyuncs.com`；有明确的功能性差异（不支持 aws-chunked 传输编码、不支持跨 region 重定向等），签名建议优先使用 virtual-hosted style。

- 官方文档《使用 Amazon S3 SDK 访问 OSS》：<https://help.aliyun.com/zh/oss/developer-reference/use-amazon-s3-sdks-to-access-oss>
- 关键差异（同页官方说明）：
  - 不支持 `aws-chunked` 传输编码（boto3 需降级 V2 签名；Java SDK 需关闭 chunkedEncoding；Go v2 的 TransferManager 大文件上传路径需注意）；
  - 不支持跨 region 自动重定向（endpoint 不匹配返回 NoSuchBucket）；
  - AWS 与 OSS 的 AK 体系独立，混用报 SignatureDoesNotMatch；时钟偏差 >15 分钟请求失败；
  - virtual-hosted style 为主（含下划线的桶名必须 path style）。

### 6. 腾讯云 COS

**结论**：COS 提供 S3 兼容实现，支持 AWS V2/V4 签名与 virtual-hosted style，endpoint 为 `cos.<region>.myqcloud.com`；官方明确"COS 不保证与 S3 完全兼容"，且 **2024-01-01 之后创建的桶不再支持 path-style 域名**。

- 官方文档《在兼容 S3 的第三方应用中使用 COS 的通用配置》：<https://cloud.tencent.com/document/product/436/41284>
- 关键点（同页）：AccessKey = SecretId / SecretKey = SecretKey；桶名格式 `<BucketName-APPID>`；仅支持"Amazon S3"且 endpoint 不可配的应用无法接入。

### 7. 华为云 OBS

**结论**：OBS 业务上兼容 AWS S3 协议（支持 V2/V4 签名，endpoint `obs.<region>.myhuaweicloud.com`），同时保留自研 OBS API（双接口模式）。**注意：官方 S3 兼容文档页 `support.huaweicloud.com/s3api-obs/obs_04_0002.html`（"OBS 兼容S3接口说明"）目前返回 404，疑似文档改版下线，未能找到当前有效的官方 S3 兼容总览页。**

- 曾经的官方文档（第三方转引，现已 404）：《OBS 兼容S3接口说明》 <https://support.huaweicloud.com/s3api-obs/obs_04_0002.html>（转引见 <https://quant67.com> 存储工程系列）
- 华为云官方 FAQ（证实 OBS SDK 为兼容 AWS S3 而保留 `acs.amazonaws.com` 常量）：《为什么SDK源码中包含acs.amazonaws.com关键字？》support.huaweicloud.com OBS SDK FAQ（2024-11 更新）
- OBS 文档总入口：<https://support.huaweicloud.com/api-obs/obs_04_0001.html>（API 参考；本轮抓取未见独立"S3 兼容"章节链接）
- **此项标注：官方一手 S3 兼容清单"当前不可达"，接入 OBS 时建议直接用 aws-sdk-go-v2 + OBS endpoint 做实测验证。**

### 8. 七牛 Kodo

**结论**：Kodo 提供 S3 兼容接口，endpoint 为 `s3.<region>.qiniucs.com`，**path-style 与 virtual-hosted style 均支持**，但必须携带 AWS 签名（不支持匿名访问）；Kodo 桶名若不全局唯一，系统会自动生成一个全局唯一的 S3 桶名（需经控制台或 GetService 获取）。

- 官方文档《S3 兼容域名》：<https://developer.qiniu.com/kodo/4088/s3>
- 同页链接的《兼容 API》文档列出支持的 S3 操作（GetService、Bucket Policy 授权、STS 临时凭证、AWS CLI/S3FS/rclone/Hadoop S3A 等工具适配）。

### 9. 百度智能云 BOS

**结论**：BOS 为对接 AWS S3 生态提供专门的"S3 兼容"文档章节（兼容签名认证、兼容接口、兼容公共头、兼容工具、服务域名），目标是让基于 S3 的应用无需改代码即可接入。

- 官方文档《S3 兼容 - Compatible Interfaces》：<https://intl.cloud.baidu.com/doc/BOS/s/Njwvyq8ho-intl-en>（页面标题已核实；国内站对应章节在 <https://cloud.baidu.com/doc/BOS/index.html> 左侧导航"S3 兼容"下）
- 兼容工具清单（官方）：rclone、S3 Browser、MinIO 客户端、Goofys 等。

### 10. Cloudflare R2

**结论**：R2 提供官方逐 API 的 S3 兼容清单：对象级核心操作（含分片上传全套、ListObjectsV2、Range/条件读、SSE-C）完整支持；**不支持** 桶 ACL/Policy/版本控制/对象 tagging/复制/事件通知/静态网站/日志/Inventory/Object Lock/Public Access Block/请求方付费等，服务端加密仅支持 SSE-C（SSE-S3/SSE-KMS 不支持）；`x-amz-acl` 一律拒绝。**StorageClass 例外：支持 `x-amz-storage-class`（仅 STANDARD/STANDARD_IA）**。分片上传支持但有限制说明；预签名 URL 支持（GET/HEAD/PUT/DELETE，1 秒~7 天，不支持 POST 表单上传）；path-style 与 virtual-hosted style 均可（官方示例两种都出现）。

- 官方 S3 API 兼容页：<https://developers.cloudflare.com/r2/api/s3/api/>
  - endpoint：`https://<ACCOUNT_ID>.r2.cloudflarestorage.com`，region 固定 `auto`（`us-east-1`/空值等价）；
  - 未实现操作：PutBucketVersioning/GetBucketVersioning、Object Lock 配置及上传/删除的 retention 头、Get/Put/DeleteObjectTagging、各桶配置类 API；
  - 分片上传注意（官方）：向同一 part number 重新上传会替换旧 part，且"若失败重试，原 part 会丢失需重传"；UploadPartCopy 不支持 copy-source 条件头。
- 官方预签名 URL 文档：<https://developers.cloudflare.com/r2/api/s3/presigned-urls/>（最长 7 天；不可配合自定义域；AWS SigV4 本地生成，无需调用 R2）。

### 11. MinIO

**结论（一句话确认）**：MinIO 是"S3 compatible object store"，对 aws-sdk-go-v2 而言按标准 S3 + 自定义 endpoint + path-style 即可接入；但其官方 GitHub 仓库已于 2026-04-25 归档为只读，社区版后续演进存在不确定性。

- 引用：<https://github.com/minio/minio>（仓库自述与归档横幅）

## C. Go 生态库现状

### 12. FTP：github.com/jlaffaye/ftp

**结论**：维护活跃（最新 release v0.2.4，2026-08-22，含安全修复），ISC 许可。支持 MLSD（服务器宣告 `MLST/MLSD` 时 `List()` 优先使用，可强制关闭）、显式 TLS FTPS（`DialWithTLS`/`DialWithExplicitTLS`，**无 implicit TLS（990 端口）选项**）、大文件流式读取（`Retr` 返回 `*Response`（io.Reader，需 Close），`RetrFrom` 支持断点 offset）。

- 仓库/README：<https://github.com/jlaffaye/ftp>
- API 文档（函数签名核实）：<https://pkg.go.dev/github.com/jlaffaye/ftp>
- 最新 release：v0.2.4（2026-08-22）：<https://github.com/jlaffaye/ftp/releases>
- 其他要点：`Stor`/`StorFrom`/`Append` 从 io.Reader 上传；`Walk` 目录遍历；`DialWithDisabledMLSD`（应对部分 Serv-U 等服务器 MLSD 有缺陷）、`DialWithTrustPasvIP`（默认不信任 PASV IP，防 SSRF）。

### 13. SFTP：github.com/pkg/sftp + golang.org/x/crypto/ssh

**结论**：pkg/sftp 活跃维护（v1.13.11，2026-07-12，BSD-2-Clause），自身不做认证/加密，依赖 golang.org/x/crypto/ssh 建立 SSH 连接：密码（`ssh.Password`）与私钥（`ssh.PublicKeys`）等认证由 `ssh.ClientConfig.Auth` 配置；host key 校验由 `HostKeyCallback` 冒调（`ssh.FixedHostKey` 固定公钥，测试可用 `ssh.InsecureIgnoreHostKey` 但不安全）。单连接并发方面：Client 并发安全，读默认并发（`UseConcurrentReads` 默认开），单文件最大并发请求数默认 64（`MaxConcurrentRequestsPerFile`），**包大小默认且上限 32768 字节**（`MaxPacketChecked` 拒绝 >32KiB），大文件复制报 `failed to send packet header: EOF` 时官方建议调小 packet。

- 仓库/README：<https://github.com/pkg/sftp>
- API 文档（ClientOption 全量核实）：<https://pkg.go.dev/github.com/pkg/sftp>
- 最新 release：v1.13.11（2026-07-12）：<https://github.com/pkg/sftp/releases>
- 已知限制（官方文档原文级）：并发写出错后目标文件可能比实际写入更长（需要在错误后 Truncate，见 `UseConcurrentWrites` 文档）；部分"一次性读取"服务器（如 stat 后即删除的 IBM 大机）需关闭并发读。

### 16. MongoDB GridFS：mongo-go-driver

**结论**：官方驱动活跃维护（v2.9.1，2026-09-10），`gridfs` 包提供真流式读写：`bucket.OpenUploadStream(name)` 得到 `io.Writer`（`UploadStream`，Close 时落库），`bucket.OpenDownloadStream(id)` 得到 `io.Reader`（`DownloadStream`，带 Read/Close/SetReadDeadline），另有 `UploadFromStream`/`DownloadToStream` 直接走 io.Reader/io.Writer——与 u-file 的流式管道模型契合度最高。

- 仓库/最新 release：<https://github.com/mongodb/mongo-go-driver/releases>（v2.9.1，2026-09-10）
- gridfs API 文档：<https://pkg.go.dev/go.mongodb.org/mongo-driver/mongo/gridfs>（v1 路径核实，v2 `go.mongodb.org/mongo-driver/v2/mongo/gridfs` 为当前主推版本，API 同构：NewBucket/OpenUploadStream/OpenDownloadStream/UploadFromStream/DownloadToStream）

### 17. MySQL BLOB：go-sql-driver/mysql

**结论**：go-sql-driver/mysql（v1.10.1，2026-09-02）**没有大 BLOB 的流式/游标读取 API——单个列值会在一次读取中整体载入内存**；驱动侧存在开放 feature request（Issue #1735 "Stream long value"，2025-08 提出，要求以 `io.Reader` 暴露 LongText/LongBlob 列）佐证该能力至今缺失。常见缓解方案 `SELECT SUBSTRING(blob_col, offset, chunk_size)` 分块读取属社区实践，**未在 go-sql-driver 或 MySQL 官方文档中作为官方推荐明确记载**（协议层面：整值随行包传输，受 `max_allowed_packet` 约束，见 MySQL 官方《Packet Too Large》文档）。

- 仓库/最新 release：<https://github.com/go-sql-driver/mysql/releases>（v1.10.1，2026-09-02）
- 流式缺失佐证（开放 issue）：<https://github.com/go-sql-driver/mysql/issues/1735>
- 社区分块实践参考（DBA StackExchange "Performance of MySQL BLOB fields processing"）：<https://dba.stackexchange.com>
- MySQL 官方协议包大小限制文档：<https://dev.mysql.com/doc/refman/8.0/en/packet-too-large.html>
- **u-file 侧结论：MySQL BLOB 文件源只能做"整值载入 + 分块 SELECT 拼接"或限制文件大小，不宜承诺大文件流式性能。**

### 18. PostgreSQL：lib/pq 与 pgx

**结论**：优先选 pgx（v5.11.0，2026-09-07，活跃）。pgx 官方支持 Large Object：`tx.LargeObjects()` 返回 `*LargeObjects`（Create/Open/Unlink），`LargeObject` 实现 `io.Reader`/`io.Writer`/`io.Seeker`/`io.Closer`，可真流式读写；**必须在事务内使用**。`bytea` 列读取与 MySQL 类似为整值载入，大文件应走 Large Object。lib/pq 未提供任何 Large Object API（godoc 无对应接口），且社区长期处于低维护状态（**注**：GitHub README 首段有"处于维护模式、建议 pgx"的表述，但本次两次抓取均未完整捕获原文，此点标注"待复核"；其 godoc 确无 Large Object 接口为实查结论）。

- pgx 仓库/最新 release：<https://github.com/jackc/pgx/releases>（v5.11.0，2026-09-07）
- pgx Large Object API 文档：<https://pkg.go.dev/github.com/jackc/pgx/v5>（`tx.LargeObjects()`；LargeObjectModeRead/Write；必须在事务内）
- lib/pq 仓库：<https://github.com/lib/pq>（godoc：<https://pkg.go.dev/github.com/lib/pq>）

## 对 u-file 方案的关键启示

1. **S3 统一适配层可行但有"暗礁"**：七家对象存储（OSS/COS/OBS/Kodo/BOS/R2/MinIO）官方都提供 S3 兼容入口，用 aws-sdk-go-v2 + 可配置 endpoint/path-style/AK 即可统一接入；但 OSS 不支持 aws-chunked、COS 2024 年后新桶禁 path-style、R2 缺版本控制/ACL/Object Lock 等，需要按源做能力开关与探测。
2. **path-style / virtual-hosted 必须做成每源可配**：MinIO、BOS、Kodo 依赖 path-style，COS 新桶、OSS 强 virtual-hosted，R2 两者皆可；一个布尔配置 + 默认值建议即可。
3. **不要指望任何现成项目的"数据库 BLOB"驱动**：AList/OpenList、Cloudreve、SFTPGo 均无数据库存储源（仅 SFTPGo 之类反向把后端暴露为 FTP）；u-file 的"MySQL/PG/MongoDB 文件源"是差异化能力，需自研。
4. **数据库源能力分级**：MongoDB GridFS（io.Reader/Writer 原生流式）和 PostgreSQL Large Object（pgx 流式，事务内）可提供大文件流式体验；MySQL BLOB 只能整值载入或 SUBSTRING 分块，应在产品上明确限制（大小上限/性能预期）。
5. **PostgreSQL Large Object 强制事务边界**：pgx 的 LargeObjects API 只能在事务内使用，u-file 的文件源会话层需为此设计长事务/读事务管理（注意 idle-in-transaction 超时）。
6. **FTP/SFTP 库选型可直接锁定**：jlaffaye/ftp（MLSD/显式 FTPS/流式 Retr）+ pkg/sftp（32KiB 包上限、并发读默认开、64 并发请求/文件）即可覆盖需求；FTPS 仅显式 TLS，隐式 990 端口暂无官方支持，需评估是否值得补。
7. **SFTP host key 校验必须做成产品能力**（known_hosts/固定指纹），不能默认 InsecureIgnoreHostKey；上传失败后的 Truncate 补偿逻辑（pkg/sftp 并发写文档明确提醒）要在传输引擎中实现。
8. **预签名 URL 设计注意平台差异**：R2 最长 7 天且不支持 POST 表单上传；国内云与 MinIO 的签名有效期策略不同，u-file 对"直传/直链"能力应按源声明有效期上限。
9. **同类项目许可需隔离**：AList/OpenList/Cloudreve/SFTPGo 均为 AGPL-3.0（Cloudreve 为 GPL-3.0），若 u-file 不打算 AGPL 开源，只能借鉴交互与协议行为、避免直接拷码；协议适配层自研 + 参考公开文档是安全路径。
10. **生态风险提示**：MinIO 官方仓库 2026-04 已归档（社区版停止公开迭代）、FileBrowser 已归档、华为 OBS 的官方 S3 兼容文档页已 404——依赖第三方的"事实标准"能力（S3 兼容）应以实测冒烟清单固化，而不是依赖文档承诺。
